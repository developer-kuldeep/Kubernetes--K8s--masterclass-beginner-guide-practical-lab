Kubernetes (K8s)

Understanding container orchestration through real-world DevOps scenarios. Learn how massive companies scale, heal, and deploy applications automatically.

1

The Problem & The Solution

Docker (The Delivery Truck)

Docker perfectly packages your application (frontend, backend, database) so it runs anywhere. But running docker run manually only spins up one container on one server.

Kubernetes (The Logistics Manager)

Kubernetes is the intelligent manager. It controls thousands of Docker trucks across multiple servers. If a truck breaks down, Kubernetes instantly replaces it automatically.

2

Real-World DevOps Scenarios

Auto-Scaling

Flipkart Big Billion Days

On a normal Tuesday, Flipkart might need 10 Backend Containers to handle user traffic.
At exactly midnight on sale day, 5 million users log in simultaneously.

How K8s Solves it: You configure a rule: "If CPU usage goes above 80%, add more containers." Kubernetes detects the massive traffic spike and automatically spins up 500 containers in seconds to prevent the site from crashing. When the sale ends, it deletes them to save AWS server costs.
Self-Healing

Zomato Server Crash

You have 3 servers running the Payment microservice. Suddenly, a hardware failure causes Server #2 to catch fire and die completely.

How K8s Solves it: You told K8s, "I ALWAYS want 3 Payment containers running." Within milliseconds of the crash, Kubernetes notices you only have 2 left. It instantly provisions a brand new Payment container on a healthy server. The customer ordering food never even notices an error.
Zero-Downtime

Netflix Updates

Netflix wants to release a new UI update. If they shut down the servers to install the update, millions of people watching movies will get disconnected.

How K8s Solves it: Rolling Updates. K8s spins up Version 2 containers alongside Version 1. It slowly shifts user traffic to Version 2. Once Version 2 is stable, it deletes Version 1. Users experience zero offline time.

Pros, Cons & When to Use It

The Advantages

  • High Availability: Applications almost never go offline due to self-healing.
  • Infinite Scaling: Easily handles unpredictable global traffic spikes.
  • Microservice Friendly: Perfectly manages complex apps split into 50+ different pieces.

The Disadvantages

  • Extremely Steep Learning Curve: Complex YAML files and heavy architecture.
  • High Infrastructure Cost: Running a minimum K8s cluster on AWS (EKS) costs $70+/month even if empty.
  • Overkill for Small Apps: Like buying a Boeing 747 to drive to the grocery store.
Rule of Thumb: Do NOT use Kubernetes for a simple college project, personal blog, or small startup. Use standard Docker or PM2. ONLY use Kubernetes when your app is huge, traffic is massive, and downtime costs millions of dollars.

The 4 Core Architectural Pillars

Ingress

Pod (App)

1. Pod (The Wrapper)

Kubernetes does not run Docker containers directly. It wraps the container inside a Pod. A Pod is the smallest unit in K8s. Usually: 1 Pod = 1 Container.

2. Deployment (The Boss)

You never create a Pod manually. You create a Deployment and tell it: "I want 3 Pods running." If a Pod dies, the Deployment acts like a boss and hires a replacement instantly.

3. Service (The Static IP)

Because Pods die and restart constantly, their IP addresses change every second. A Service sits in front of the Pods and provides ONE permanent, unchanging IP address for other apps to talk to.

4. Ingress (The Traffic Cop)

It looks at the URL the user typed and routes traffic. Example: If they type netflix.com/login, it routes to the Auth Service. If they type netflix.com/movies, it routes to the Streaming Service.

Practical Lab: Deploying an App

Let's prove the magic works. We will write a declarative YAML blueprint asking Kubernetes to run 3 copies of an Nginx web server, and expose it to the internet.

Step 1: Write the Blueprint (Deployment YAML)

Create a file named app-deployment.yaml. This instructs the K8s "Boss" to maintain 3 replicas of the app.

app-deployment.yaml
apiVersion: apps/v1 kind: Deployment metadata: name: my-web-app spec: replicas: 3 # We want 3 identical containers running! selector: matchLabels: app: frontend template: metadata: labels: app: frontend spec: containers: - name: nginx-container image: nginx:latest # The Docker image to use ports: - containerPort: 80

Step 2: Tell Kubernetes to Build It

We use the kubectl command-line tool to talk to our Kubernetes cluster.

Terminal
# Apply the blueprint to the cluster kubectl apply -f app-deployment.yaml # Verify that 3 Pods are now running kubectl get pods

Step 3: Expose it to the Internet (Service)

The pods are running, but invisible to the outside world. We must create a LoadBalancer Service to route internet traffic to them.

Terminal
# Create a Load Balancer Service kubectl expose deployment my-web-app --type=LoadBalancer --port=80 --target-port=80 # Get the public IP address to view the website in your browser kubectl get svc

Try the Self-Healing Magic

Run kubectl get pods and copy the name of one pod.
Force-delete it: kubectl delete pod <paste-pod-name>
Instantly run kubectl get pods again. You will see K8s has already created a brand new pod (Age: 1s) to replace the one you killed!

Top 5 Interview Questions

Q1. What is the fundamental difference between Docker and Kubernetes?

Answer: Docker is a containerization engine used to build and run individual containers on a single machine. Kubernetes is an orchestration platform that manages, scales, and heals thousands of Docker containers across multiple clustered servers.

Q2. What is a Pod?

Answer: A Pod is the smallest and most basic deployable object in Kubernetes. It represents a single instance of a running process in your cluster and typically contains one Docker container (though it can contain multiple tightly-coupled containers).

Q3. Why do we use a Deployment instead of creating Pods directly?

Answer: If a Pod is created manually and it crashes, it dies forever. A Deployment is a controller that guarantees a specified number of Pod replicas are running at all times. It enables self-healing and zero-downtime rolling updates.

Q4. How does Kubernetes provide Zero-Downtime deployments?

Answer: Using "Rolling Updates". When you push a new version of an app, K8s slowly spins up new Pods with the V2 code. Once the V2 Pods are healthy, it routes traffic to them and terminates the old V1 Pods one by one, ensuring the application never goes completely offline.

Q5. What is the difference between a ConfigMap and a Secret?

Answer: Both are used to decouple configuration from the Docker image. A ConfigMap is used to store plain-text, non-sensitive data (like PORT numbers or URLs). A Secret is used to securely store sensitive data (like Database Passwords, SSH keys, or TLS certificates) using Base64 encoding.
